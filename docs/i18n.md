# Internationalization (i18n)

ポータルの多言語対応 (日本語と英語) の URL 戦略、lang 解決ルール、リソース運用、翻訳なし fallback。`architecture.md` の zones に従い、i18n runtime は `app/lib/i18n/` に集約する。

## URL 戦略

**URL から lang を排除し Cookie で管理する**。同じ path が両言語を表す:

```
/                              top
/databases/bioproject          database detail
/search/results?q=cancer       search results
/news                          news index
```

SwitchLang を踏んでも URL は変わらず、ページ全体が in-place で切り替わる。

この URL 戦略が保証する性質:

- 主要 URL を共有しやすい (`/databases/bioproject` のような短い形)。SwitchLang で URL が変わらないため UX が連続する
- SEO は sitemap.xml が `?lang=ja` / `?lang=en` の 2 entry に hreflang を出力することで担保し、crawler / 共有 URL から特定言語を踏める (本書「SEO」)
- 「同じ URL を共有すると相手の cookie 次第で言語が変わる」 副作用は `?lang=xx` の hint URL で救済できる (日常 share では `/foo` を渡し、特定言語固定が必要な場合のみ `?lang=en` を共有)
- CDN cache は `Vary: Cookie` で言語ごとに分かれるが、`db_portal_lang` の値域は 2 値 (`ja` / `en`) しかなく許容範囲
- 共有 URL から検索 DSL の query (`?q=` 等) と lang が混ざらない (`?lang=` は SwitchLang のような内部 navigation で付かない)

### lang 解決の優先順位

1. URL の `?lang=ja|en` (読み取り専用 hint)
2. cookie `db_portal_lang` (`ja` or `en`)
3. `Accept-Language` ヘッダ (`ja*` を優先、`en*` なら `en`、それ以外は ja)
4. fallback `ja`

`?lang=ja|en` が指定されたときは root loader が cookie を上書きし、`?lang` を落とした URL に 302 redirect する (cookie を「stick」 させた状態で URL を綺麗にする)。初回訪問で cookie が無く Accept-Language で言語が決まった場合も cookie を発行する。

priority chain は純粋関数 `resolveLangFromRequest` (`app/lib/i18n/resolve-lang.server.ts`) に閉じ込め、PBT で「任意入力に対して常に `ja|en` を返す」「`?lang=ja|en` 指定時はその値を返す」 不変量を担保する。

## root loader での処理

`app/root.tsx` の `loader` が次を順に行う:

1. URL の `?lang=ja|en` を検出したら cookie を立てて `?lang` を落とした URL に 302 redirect
2. cookie が無ければ `Accept-Language` から推定し、決定値で cookie を新規発行 (sticky)
3. cookie 既出ならその値を採用
4. `lang` を loaderData に乗せ、`<LangProvider>` で全 component に配る

`lang` は loaderData として配下に届き、`<LangProvider value={lang}>` 経由で `useLang` で取り出せる。

## useLang hook の挙動

- Provider 配下でなければ throw (SSR で root loader → Provider の経路を必須にし、暗黙の default 値が紛れ込まないようにする)
- 戻り値の型は `"ja" | "en"`
- `useT` (`react-i18next` ベース) の lang を Provider と同期する

## lang cookie 仕様

`app/lib/i18n/lang-cookie.server.ts` で定義する。

| attr | 値 | 根拠 |
|---|---|---|
| name | `db_portal_lang` | 既存 `sid` cookie 命名 (短い snake) と整合、prefix で衝突回避 |
| HttpOnly | false | lang は機密でない。client からも参照可能 |
| SameSite | Lax | 既存 `sid` と揃える。Strict だと top-level navigation で消える |
| Secure | secureRuntime(env) | dev (http origin) では落とす |
| Path | `/` | 全 URL で同じ lang |
| Max-Age | 60×60×24×365 (1 年) | 言語選択は長持ちさせる |
| Domain | 未指定 | サブドメイン共有不要 |

## SwitchLang resource route

`app/routes/api.set-lang.ts` を resource route として定義する (default export なし、`action` のみ)。`useFetcher().submit({ lang }, { method: "post", action: "/api/set-lang" })` で submit すると RR は全 active loader を revalidate するため、root loader が新 lang を返し → `<LangProvider>` 値が変わり → 全 page が新 lang で再 render される。URL は変化しない。

action の処理は: `{ lang: "ja" | "en" }` を Zod parse → `Set-Cookie: db_portal_lang=...` を付けて Referer (もしくは `/`) に 303 redirect。

Header の `SwitchLang` も `<TranslationUnavailable>` の「Switch to Japanese」 動線も、共通でこの resource route に POST する `<fetcher.Form>` で実装する。

## リソース運用

### ファイル配置

```
app/lib/i18n/
├── index.ts                  i18next init + 公開 API (createI18nInstance)
├── use-lang.ts               useLang hook (Context 参照)
├── use-t.ts                  useT hook (react-i18next wrapper)
├── lang-context.tsx          LangProvider / LangContext
├── lang-cookie.server.ts     cookie 定義 (server 専用)
├── resolve-lang.server.ts    priority chain (server 専用)
└── resources/
    ├── ja.ts                 ja リソース
    └── en.ts                 en リソース
```

リソースは **静的 import** する (ja / en の 2 言語、合計サイズが小さく、初期描画時に必ず使う)。

### キー設計

ネスト構造を平坦化したドット記法で扱う。namespace の主な区分: `common` / `nav` / `breadcrumb` / `switchLang` / `translationUnavailable` / `notificationBar` / `newsAside` / `auth` / `footer` / `a11y` / `errors` / `search` / `submit` / `top`。

`en.ts` も **同じキー構造** を持つ。キーセットの整合は PBT (`tests/pbt/lib/i18n/resource-parity.pbt.test.ts`) で検証する。

### request-scoped i18next instance

`createI18nInstance(lang)` を 1 request ごとに呼び、`<I18nextProvider i18n={instance}>` に渡す。これにより SSR の並列 request で `changeLanguage` のレースが発生しない。module-level の global instance は持たない。

設定:

- `resources: { ja: { translation: ja }, en: { translation: en } }`
- `lng: lang`
- `fallbackLng: "ja"` (en に未定義のキーは ja で fallback)
- `interpolation: { escapeValue: false }`

## 翻訳なし fallback

### 挙動

en でレンダリング中に対応キーが en リソースに存在しない場合:

1. ja のキーを fallback として表示する (page が空にならない)
2. `<TranslationUnavailable />` バナーをページ上部に表示する
3. バナーには「Switch to Japanese」 リンクで cookie 切替する動線を置く (URL 不変)

### TranslationUnavailable バナー

`app/shell/translation-unavailable.tsx` で実装する。現在 lang が `en` かつ いずれかの match の `handle.i18n.en` が `"complete"` 以外であれば表示する。ja 表示時は何も表示しない。

「Switch to Japanese」 部分は `<fetcher.Form method="post" action="/api/set-lang">` + hidden `lang=ja` の link 風 button で実装する。submit すると root loader が再評価され、URL を変えずに ja に切り替わる。

route handle 規約は `architecture.md` の「route handle 規約」 を参照。

## SEO

### hreflang 宣言

`app/root.tsx` の `meta()` で、現在 path について次の 3 つの `<link rel="alternate">` を出力する:

| hrefLang | href |
|---|---|
| `ja` | `${origin}${pathname}?lang=ja` |
| `en` | `${origin}${pathname}?lang=en` |
| `x-default` | `${origin}${pathname}?lang=ja` |

`?lang=` を踏んだ crawler は root loader の redirect で cookie が立った状態の path に着地し、目的の言語で indexable になる。

### sitemap.xml / robots.txt

`server/api/sitemap.ts` (`GET /sitemap.xml`) が、content collection (`databases`) + 静的 routes (`/` / `/search` / `/submit` / `/news`) について `?lang=ja` / `?lang=en` の 2 URL を出力する。各 `<url>` 内に `<xhtml:link rel="alternate" hreflang="ja|en|x-default">` を相互宣言する (Google 推奨形式)。`<urlset>` は `xmlns:xhtml="http://www.w3.org/1999/xhtml"` を宣言する。`<loc>` は production origin (`DB_PORTAL_PORTAL_ORIGIN`) を base に固定、`<changefreq>` / `<priority>` は出さない (Google は無視する)。

`server/api/robots.ts` (`GET /robots.txt`) は `DB_PORTAL_ENV=production` のみ `User-agent: *` + `Allow: /` + `Sitemap: {origin}/sitemap.xml` を返す。dev / staging では `User-agent: *` + `Disallow: /` を返して crawler indexing を回避する。
