# Internationalization (i18n)

ポータルの多言語対応 (日本語と英語) の URL 戦略、lang 解決ルール、リソース運用、翻訳なし fallback。`architecture.md` の zones に従い、i18n runtime は `app/lib/i18n/` に集約する。

## URL 戦略

**URL から lang を排除し Cookie で管理する**。同じ path が両言語を表す:

```
/                              top
/databases/bioproject          database detail
/search/results?q=cancer       search results
/news                          news index
```

SwitchLang を踏んでも URL は変わらず、ページ全体が in-place で切り替わる。

この URL 戦略が保証する性質:

- 主要 URL を共有しやすい (`/databases/bioproject` のような短い形)。SwitchLang で URL が変わらないため UX が連続する
- SEO は sitemap.xml が `?lang=ja` / `?lang=en` の 2 entry に hreflang を出力することで担保し、crawler / 共有 URL から特定言語を踏める (本書「SEO」)
- 「同じ URL を共有すると相手の cookie 次第で言語が変わる」 副作用は `?lang=xx` の hint URL で救済できる (日常 share では `/foo` を渡し、特定言語固定が必要な場合のみ `?lang=en` を共有)
- CDN cache は `Vary: Cookie` で言語ごとに分かれるが、`db_portal_lang` の値域は 2 値 (`ja` / `en`) しかなく許容範囲
- 共有 URL から検索 DSL の query (`?q=` 等) と lang が混ざらない (`?lang=` は SwitchLang のような内部 navigation で付かない)

### lang 解決の優先順位

1. URL の `?lang=ja|en` (読み取り専用 hint。root loader が処理し、302 redirect で cookie に変換する)
2. cookie `db_portal_lang` (`ja` or `en`)
3. `Accept-Language` ヘッダ: q-weight 降順で並べ、`ja` / `en` のいずれかに一致した最初の言語を採用
4. fallback `DB_PORTAL_DEFAULT_LANG` (default `ja`)

`?lang` hint の検出と redirect は root loader の責務、cookie / Accept-Language / default の chain は純粋関数 `resolveLang` (`app/lib/i18n/resolve-lang.server.ts`) の責務、と役割が分かれる。`resolveLang` は `?lang` を引数に取らず、root loader が hint 不在を確かめてから呼ぶ。hint の検出だけは同ファイルの `detectLangHint` が担う。

`resolveLang` は PBT で「cookie / Accept-Language / default の chain が任意入力に対し常に `ja|en` を返す」 不変量を担保する。

## root loader での処理

`app/root.tsx` の `loader` が優先順位 chain に上乗せする処理:

- URL の `?lang=ja|en` を検出したら cookie を立てて `?lang` を落とした URL に 302 redirect する (cookie を「stick」 させた状態で URL を綺麗にする)
- cookie が無いまま `resolveLang` で言語が決まった初回訪問では、決定値で cookie を新規発行 (sticky)
- 決定した `lang` を loaderData に乗せ、`<LangProvider value={lang}>` 経由で全 component に配る (`useLang` で取り出す)。loaderData には `lang` の他に `cspNonce` / `portalOrigin` 等が同梱される

## useLang hook の挙動

- Provider 配下でなければ throw (SSR で root loader → Provider の経路を必須にし、暗黙の default 値が紛れ込まないようにする)
- 戻り値の型は `"ja" | "en"`
- `useT` (`react-i18next` ベース) の lang を Provider と同期する

## lang cookie 仕様

`app/lib/i18n/lang-cookie.server.ts` で定義する。

| attr | 値 | 根拠 |
|---|---|---|
| name | `db_portal_lang` | 既存 `sid` cookie 命名 (短い snake) と整合、prefix で衝突回避 |
| HttpOnly | 未指定 (cookie lib のデフォルト = false) | lang は機密でない、client からも参照可能 |
| SameSite | Lax | 既存 `sid` と揃える。Strict だと top-level navigation で消える |
| Secure | secureRuntime(env) | dev (http origin) では落とす |
| Path | `/` | 全 URL で同じ lang |
| Max-Age | 60×60×24×365 (1 年) | 言語選択は長持ちさせる |
| Domain | 未指定 | サブドメイン共有不要 |

## SwitchLang resource route

`app/routes/api.set-lang.ts` を resource route として定義する (default export なし、`action` のみ)。`useFetcher().submit({ lang }, { method: "post", action: "/api/set-lang" })` で submit すると RR は全 active loader を revalidate するため、root loader が新 lang を返し → `<LangProvider>` 値が変わり → 全 page が新 lang で再 render される。URL は変化しない。

action の処理は: `{ lang: "ja" | "en" }` を Zod parse → `Set-Cookie: db_portal_lang=...` を付けて Referer (もしくは `/`) に 303 redirect。

Header の `SwitchLang` も `<TranslationUnavailable>` の「Switch to Japanese」 動線も、共通でこの resource route に POST する `<fetcher.Form>` で実装する。

## リソース運用

### ファイル配置

i18n runtime は `app/lib/i18n/` に集約する。主要モジュール:

| モジュール | 責務 |
|---|---|
| `lang-cookie.server.ts` | `db_portal_lang` cookie の serialize / parse (server 専用) |
| `resolve-lang.server.ts` | cookie / Accept-Language / default の chain と `?lang` hint 検出 (server 専用) |
| `lang-context.tsx` | `LangProvider` / `LangContext` |
| `category-label.ts` / `service-category-label.ts` | `NewsCategory` / `ServiceCategory` → i18n key の写像 |
| `resources/ja.ts` / `resources/en.ts` | 翻訳リソース本体 |

これ以外の helper (`index.ts` の i18next init、`use-lang.ts` / `use-t.ts` hook、`flatten-keys.ts`、`format-date.ts`) も同ディレクトリに置く。`format-date.ts` は ISO 日付を `YYYY/MM/DD` 形に整形するだけで lang には依存しない (日付表記は両言語共通)。

リソースは **静的 import** する (ja / en の 2 言語、合計サイズが小さく、初期描画時に必ず使う)。

### キー設計

ネスト構造を平坦化したドット記法で扱う。namespace の集合は `resources/ja.ts` が SSOT で、`en.ts` も **同じキー構造** を持つ。両者のキーセット整合は PBT (`tests/pbt/lib/i18n/resource-parity.pbt.test.ts`) が担保する。a11y 用の文言は `a11y` namespace 配下に置き、たとえば SwitchLang button の aria-label は `a11y.languageSwitcher` を引く。

### request-scoped i18next instance

`createI18nInstance(lang)` を 1 request ごとに呼び、`<I18nextProvider i18n={instance}>` に渡す。これにより SSR の並列 request で `changeLanguage` のレースが発生しない。module-level の global instance は持たない。

設定:

- `resources: { ja: { translation: ja }, en: { translation: en } }`
- `lng: lang`
- `fallbackLng: "ja"` (en に未定義のキーは ja で fallback)
- `interpolation: { escapeValue: false }`

## 翻訳なし fallback

### 挙動

en でレンダリング中に対応キーが en リソースに存在しない場合:

1. ja のキーを fallback として表示する (page が空にならない)
2. `<TranslationUnavailable />` バナーをページ上部に表示する
3. バナーには「Switch to Japanese」 リンクで cookie 切替する動線を置く (URL 不変)

### TranslationUnavailable バナー

バナーの表示条件・表示位置・スタイルは `frontend.md` の「Shell」§ TranslationUnavailable が SSOT (`app/shell/translation-unavailable.tsx`)。i18n 観点で担保するのは、「Switch to Japanese」 が `<fetcher.Form method="post" action="/api/set-lang">` + hidden `lang=ja` の link 風 button で、submit すると root loader 再評価で URL を変えずに ja へ切り替わる点 (上記「SwitchLang resource route」 と同じ機構) のみ。route handle 規約は `architecture.md` の「route handle 規約」 を参照。

## SEO

### hreflang 宣言

`app/root.tsx` の `meta()` で、現在 path について次の 3 つの `<link rel="alternate">` を出力する:

| hrefLang | href |
|---|---|
| `ja` | `${origin}${pathname}?lang=ja` |
| `en` | `${origin}${pathname}?lang=en` |
| `x-default` | `${origin}${pathname}?lang=ja` |

`?lang=` を踏んだ crawler は root loader の redirect で cookie が立った状態の path に着地し、目的の言語で indexable になる。

### document title

`app/root.tsx` の `meta()` が共有 meta tag (viewport / charset / icon / hreflang) と既定 title `BSI` を出力する。各 content route は共有 `pageTitleMeta` を `meta` として export し、root の共有 tag を引き継いだまま title だけを per-route の値に差し替える (child route の `meta` は root を置換するため、root tag を引き継いで title のみ上書きする)。

title は **逆パンくず形式・英語固定** で、UI 言語 (ja / en) に関わらずローカライズしない (ブランド表記を一貫させるため)。各 route の `handle.titleSegments` (static) / `handle.titleResolver` (dynamic) を `resolvePageTitle` (`app/lib/content/page-title.ts`) が leaf-first に走査し、segment を逆順に並べて末尾へ `BSI` を足す。宣言の無い route (top / auth callback 等) は `BSI` 単体になる。route handle 規約は `architecture.md`「route handle 規約」を参照。

| route | `<title>` |
|---|---|
| `/` | `BSI` |
| `/search` | `Search \| BSI` |
| `/search/results` | `Results \| Search \| BSI` |
| `/submit` | `Submit \| BSI` |
| `/news` | `News \| BSI` |
| `/services` | `Services \| BSI` |
| `/databases/:slug` | `{DB title (en)} \| Databases \| BSI` |

### sitemap.xml / robots.txt

`server/api/sitemap.ts` (`GET /sitemap.xml`) が、content collection (`databases`) + 静的 routes (`/` / `/search` / `/submit` / `/news`) について `?lang=ja` / `?lang=en` の 2 URL を出力する。各 `<url>` 内に `<xhtml:link rel="alternate" hreflang="ja|en|x-default">` を相互宣言する (Google 推奨形式)。`<urlset>` は `xmlns:xhtml="http://www.w3.org/1999/xhtml"` を宣言する。`<loc>` は production origin (`DB_PORTAL_PORTAL_ORIGIN`) を base に固定、`<changefreq>` / `<priority>` は出さない (Google は無視する)。

`server/api/robots.ts` (`GET /robots.txt`) は `DB_PORTAL_ENV=production` のみ `User-agent: *` + `Allow: /` + `Sitemap: {origin}/sitemap.xml` を返す。dev / staging では `User-agent: *` + `Disallow: /` を返して crawler indexing を回避する。

## テスト

### PBT: ja / en キー整合

`tests/pbt/lib/i18n/resource-parity.pbt.test.ts` で `ja` / `en` の同一キーセット保有を検証する。`flattenKeys` (`app/lib/i18n/flatten-keys.ts`) でネストオブジェクトを `"a.b.c"` 形のドット記法に展開し、両 set の同一性を確認する。

### PBT: resolve-lang priority chain

`tests/pbt/lib/i18n/resolve-lang.pbt.test.ts` で次を担保 (`?lang` は `resolveLang` の責務外なので 2 関数を分けて検証する):

- `resolveLang`: 任意の cookie / Accept-Language 入力に対し戻り値は必ず `"ja"|"en"`
- `detectLangHint`: `?lang=ja|en` を検出してその値を返し、不正値 / 不在では null を返す (root loader が hint 不在を確かめてから `resolveLang` を呼ぶ)

### Unit: cookie / resource route / Context

- `tests/unit/lib/i18n/lang-cookie.test.ts`: serialize → parse round-trip、attributes 検証
- `tests/unit/lib/i18n/resolve-lang.test.ts`: priority chain 境界値 (`?lang=invalid` で fall through 等)
- `tests/unit/lib/i18n/lang-context.test.tsx`: `<LangProvider value="en">` で `useLang() === "en"`、Provider 無しで throw
- `tests/unit/routes/api.set-lang.test.ts`: `createRoutesStub` で fetcher submit、303 / Set-Cookie / Location 検証
- `tests/unit/shell/switch-lang.test.tsx`: fetcher.submit が `/api/set-lang` に POST されること
- `tests/unit/shell/translation-unavailable.test.tsx`: fetcher Form の hidden lang=ja が POST されること
